# ACME 库存系统概览

[English](system-overview.md) | **简体中文**

ACME 支持食品银行从接收捐赠物资到向接收方发放物资的业务。
系统按批次管理库存，为订单预留物资，并记录库存变动，帮助团队了解当前余额及其变化历史。

本文介绍系统用途、业务概念、组成和运行环境，面向操作人员、项目相关方、测试、开发及维护人员。
详细操作、代码定位和配置步骤由所链接的专题文档说明。

本文描述已经实现的系统。业务和架构基线为截至 `cd4aba2` 的批次库存版本；
后续文档改动用于解释该基线，并不代表新增应用功能。

## 用途与范围

食品银行操作人员可以维护商品资料、接收捐赠、查看批次有效期、预留和发放物资、
记录盘点或损耗，以及导出报表。概览仪表盘会突出显示需要关注的库存。

捐赠者提供物资，接收方领取物资，但目前双方都没有专用门户或登录角色，
其信息由操作人员录入。所有注册用户拥有相同的业务操作权限。
当前应用覆盖库存和物资发放，不包含采购、支付或物流追踪。

## 核心业务概念

| 概念 | 含义 |
| --- | --- |
| 商品（Product） | 由 SKU 标识的一类物资，具有名称、别名、类别和基础单位 |
| 批次（Batch） | 商品的一次入库记录，具有独立的来源、收货日期和到期日期 |
| 实物库存（On-hand stock） | 系统记录的实际在库数量，包括当前不能发放的物资 |
| 预留库存（Reserved stock） | 已分配给尚未完成的接收方订单的数量 |
| 可用库存（Available stock） | 符合发放条件的实物库存减去预留量；过期或隔离的物资不计入 |
| 订单（Order） | 接收方所需的商品及数量，并记录计划发放日期 |
| 库存流水（Stock movement） | 入库、预留、发放、盘点、报损或批次状态变化的记录 |

数量均以各商品的基础单位表示，例如袋或盒，只支持整数，不进行自动单位换算。
余额计算示例和实体关系见[数据模型（英文）](data-model.md)。

## 主要业务流程

| 任务 | 主要操作 | 对库存的影响 |
| --- | --- | --- |
| 接收物资 | 选择或创建商品，在 Donations 中登记带日期的批次 | 增加实物库存，保留之前的批次 |
| 计划发放 | 选择商品、填写接收方信息并预览可用库存 | 展示分配方案，不预留库存 |
| 确认订单 | 重新检查可用量并分配符合条件的批次 | 增加预留量，实物库存不变 |
| 完成发放 | 校验预留批次并记录发放 | 减少实物库存，同时释放对应预留量 |
| 取消订单 | 填写原因并取消处于预留状态的订单 | 释放预留量，不扣减实物库存 |
| 修正或限制库存 | 记录实盘、报损、隔离或解除隔离 | 更新余额或发放资格，并记录原因 |
| 检查库存 | 查看最低库存和到期提醒、流水与报表 | 提供信息，不改变余额 |

订单优先使用最早到期的批次，即 FEFO（first expiry, first out，先到期先出）。
预览不会锁定库存，因此确认订单时会再次检查可用量。
过期物资不能用于发放；迁移后的历史订单保持只读，不产生新的预留或扣减。

[业务流程文档（英文）](workflows.md)提供操作细节、业务流程图和状态图。
其中的时序图说明软件如何处理成功操作及失败情况。库存事务失败时，不会留下部分余额变更。

## 系统组成

应用由四个主要部分组成：

- 浏览器界面：用于管理库存、捐赠、订单、流水和报表。
- Flask 应用：提供页面、处理请求并执行业务规则。
- SQLite 数据库：保存账户、商品、批次、订单和库存流水。
- 本地文件存储：保存上传图片和运行配置相关文件。

系统以一个模块化 Python 应用交付，并未拆成多个独立部署的服务。
页面和 JavaScript 由同一个应用提供。
系统上下文、运行组成、模块职责及页面导航见[架构文档（英文）](architecture.md)；
数据库关系见 [ER 图（英文）](data-model.md#entity-relationships)。

## 运行与维护概况

用户通过浏览器访问应用。仓库中的本地启动操作使用 `http://127.0.0.1:5055`；
直接使用 Flask 默认启动方式时，端口为 5000。
这些地址指向运行应用的本机，不是托管的公共服务。

安装步骤见 [README](../README.zh-CN.md#安装与启动)。
应用不附带账户凭据或示例库存；全新数据库通过注册创建账户。
已有安装需要按文档执行升级。

数据库和上传目录由配置决定，默认存放于 Flask 的私有实例目录；
在可编辑安装的源码布局中，通常是 `src/instance`。
升级已有数据库前会创建备份。账户信息、上传文件、密钥及备份属于运行数据，
应与源码仓库分开管理。

配置细节见[配置与本地部署（英文）](development.md#configuration)。
升级或恢复前，请阅读[迁移与恢复（英文）](data-model.md#migration-and-recovery)。
撤销代码提交并不会恢复数据库内容。

## 当前限制与设计取舍

| 方面 | 当前行为及影响 |
| --- | --- |
| 访问权限 | 所有注册用户具有相同业务权限，尚无基于角色的审批流程 |
| 库存范围 | 不支持库位、小数数量或单位换算；商品产生库存历史后，基础单位不能改变 |
| 业务集成 | 捐赠者和接收方仅以文本记录，没有独立的账户或实体表；不包含采购、物流集成 |
| 一致性 | 库存变更与流水一起提交；SQLite 在计算余额前串行化库存写操作 |
| 审计历史 | 业务流程追加流水记录，但数据库不是防篡改的审计存储 |
| 运行环境 | 已说明本地部署方式，仓库尚未配置生产基础设施 |
| 自动化 | 尚未实现 Agent、模型训练或后台任务处理流程 |

业务日期使用服务器本地日期，流水时间戳使用 UTC。
更换数据库引擎时，需要重新审视迁移方式和并发控制。
未来功能应标为规划内容，不应出现在描述当前系统的图中。
